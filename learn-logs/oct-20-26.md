## oct 20, 2026

#### the goal  
deploying an ec2 with a basic web server (httpd, in a vm named `nginx-vm`), which has a private sg to control inbound/outbound traffic,
alongside 2 s3 buckets - one the ec2 can access (through iam entities) and one that is forbidden. 

> note: only the accessible bucket (`my-bucket-1`) made it into `main.tf` - the forbidden bucket is still a todo

#### related resources 
- ec2
- iam-role-and-policy: deploys the iam role, policy, and outputs the instance_profile for the ec2 access
- s3-bucket

#### what went wrong?

at first the instance profile didn't seem to attach to the ec2, so i added a few troubleshooting outputs and depends_on. 

when applied, terraform showed the vm had an instance profile attached, but in the aws ui and in the vm itself the field was empty.

eventually, it turned out that the aws ui was on one region and the code deployed to another, which means the dashboard was showing information from a different region. 

#### what did i learn (from the flow of the project, not the module building)
- troubleshooting in the aws ui and in the ec2 connect panel 
- troubleshooting in the terraform cli 
- aws regions and deploying resources in multiple regions 
  - some aws objects are global, like iam entities, and some are per region, like ec2 
  - always check the region selector in the console before assuming a resource is missing
- the iam chain for giving an ec2 access to a bucket: policy -> role -> instance profile -> ec2 (see the [iam-role-and-policy learn log](../modules/iam-role-and-policy/learn-log.md))
- `aws_vpc_security_group_ingress_rule` vs `aws_security_group`
  - define the empty security group with `aws_security_group`
  - later on, use `aws_vpc_security_group_ingress_rule` or `aws_vpc_security_group_egress_rule` to define more specific single rules in the sg (inbound/outbound traffic)
